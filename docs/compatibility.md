# OpenWrt compatibility and validation

[English README](../README.md) · [中文说明](../README.zh.md)

The supported integration targets are **x86/64, x86_64, musl**. OpenWrt 23.05/24.10 use opkg and native IPK; OpenWrt 25.12 switched to APK. A single APK built with the 25 SDK is not a supported installation method on 23/24. The distinction is reflected in SDK selection, source packaging revision, native package assembly, verification, and installation instructions.

## Pinned targets

All fixed values live in `config/build.json`; this table describes the current defaults.

| Profile | Exact release | SDK GCC / archive | Package format | Release output |
| --- | --- | --- | --- | --- |
| `23.05` | 23.05.6 | 12.3.0 / xz | IPK, revision `-N` | `dist/release-23.05.6-x86_64/` |
| `24.10` | 24.10.6 | 13.3.0 / zstd | IPK, revision `-N` | `dist/release-24.10.6-x86_64/` |
| `25.12` (default) | 25.12.1 | 14.3.0 / zstd | APK 3, revision `-rN` | `dist/release/` |

OpenWrt uses series names 23.05, 24.10, and 25.12, rather than a universal major-version ABI. To target another patch release, update the corresponding SDK/version/checksum/image pins together and validate against that exact image. Runtime APIs are shared by the three supported series, but this is not a claim that every patch release or downstream firmware has been tested. Versions older than 23.05 and non-x86_64 architectures are outside the current support scope. Compatibility with a legacy series does not extend upstream security maintenance.

The public source and release metadata used to establish this matrix are:

- [Official OpenWrt release downloads](https://downloads.openwrt.org/releases/), including [23.05.6](https://downloads.openwrt.org/releases/23.05.6/targets/x86/64/), [24.10.6](https://downloads.openwrt.org/releases/24.10.6/targets/x86/64/), and [25.12.1](https://downloads.openwrt.org/releases/25.12.1/targets/x86/64/).
- [OpenWrt 25.12 announcement](https://lists.openwrt.org/pipermail/openwrt-announce/2026-March/000081.html), describing the package-manager transition.
- [OpenWrt 23.05 rpcd package definitions](https://github.com/openwrt/openwrt/blob/openwrt-23.05/package/system/rpcd/Makefile), including `rpcd-mod-ucode`; the LuCI backend does not require an APK-specific runtime API.
- [Docker Engine installation documentation](https://docs.docker.com/engine/install/).

## Common functionality

All profiles package the same reviewed daemon/client sources, procd service, UCI validation, non-root execution, private-LAN listener checks, opt-in DNS SRV management, and LuCI view/RPC/ACL/translation files. LuCI includes configuration save/apply, start/stop/restart, status and memory/listener information, log viewing/download, and v4/v5/v6 diagnostics. No periodic activation traffic is generated by status polling.

SDK preparation accounts for the older integrated base-package tree and xz archive format on 23.05. Feed revisions remain those shipped by each official SDK. SDK extraction/build caches and older release outputs are isolated; upstream source objects and deterministic archives are shared.

Native IPKs retain their original control/data archives for opkg. SDK fakeroot runs with the matching SDK host tools; assembly rejects any leaked host UID/GID in application packages. The release bundle is authenticated using a detached signature over `SHA256SUMS`, verified against a trusted public key on the build host. opkg uses its configured official feed trust for dependencies. APKs retain individual package signatures and offline deployment checks.

The APK transaction engine, reviewed-plan state binding, automatic rollback, and ownership-aware transactional uninstall remain available only on 25.12. IPK releases are rejected before an SSH transaction starts. On 23/24 install/remove packages through native opkg as documented in the READMEs; configuration backup and any recovery remain the operator's responsibility.

All three pinned profiles built successfully with four application packages each. All release hashes/signatures and x86_64/musl ELF hardening checks passed. **38 unit tests**, JavaScript syntax checking, and ShellCheck error checks passed.

Detailed local evidence includes `dist/ipk-integration-23.05.6.json`, `dist/ipk-integration-24.10.6.json`, `dist/reproducibility-<version>.json`, and `dist/verification/<version>/`. Browser captures are `dist/luci-23.05.png`, `dist/luci-23.05-zh.png`, and `dist/luci-24.10-zh.png`. These files are deliberately excluded from Git because test/deployment reports can contain device configuration.

- Unit regressions cover profile isolation, frozen snapshots, package-version syntax, tar/ar IPK parsing, and rejection of IPKs before any deployment SSH call, in addition to the existing source/cache/transaction/timeout tests.
- `scripts/verify-artifacts.sh` checks release hashes, APK signatures or IPK bundle signatures, x86_64/musl ELF metadata, PIE, RELRO, immediate binding, and non-executable stacks.
- `tests/ipk_integration.py` verifies the QEMU model, exact release, and opkg before mutation. It installs native IPKs, tests disabled defaults, dedicated-user execution, protocol diagnostics, LuCI actions/logs, backend validation, authenticated HTTP RPC/UCI permissions, translation assets, DNS publish/revoke, power-cycle autostart, and configuration-preserving uninstall. Guest readiness uses a separate 120-second test budget for TCG emulation; this does not change deployment/recovery limits. Autostart is checked by a cold VM restart with its disk retained, rather than qualifying firmware warm-reset behavior.
- `scripts/reproducibility.py` compares the three binaries and all four unsigned native packages across clean package rebuilds in the same pinned SDK. Signed release verification is separate.

The fresh 25.12 guest also verified unprivileged VM-container startup as host UID/GID `501:20`. Runtime dependencies were installed from official feeds before the APK transaction suite; its application deployments then used the offline transaction path.

The guest and browser results above were obtained on macOS with OrbStack's Docker API and amd64 builder containers. A separate native Linux Docker Engine run is recorded below. The manually dispatched GitHub workflow remains available for future Linux build checks.

Historical 25.12.1 router deployment, browser, upgrade and failure-recovery evidence remains in [validation.md](validation.md), [review.md](review.md), and [recovery.md](recovery.md). Do not reinterpret those earlier hashes or test results as validation of a new build. This compatibility task uses disposable guests and does not redeploy the physical router.
